## The five pieces

| Piece | Its job | Example in the user feature |
| --- | --- | --- |
| DTO | Describe and validate request data | `CreateUserDto` accepts a name |
| Controller | Match an HTTP route and return a response | POST `/user` calls the service |
| Service or handler | Coordinate one application operation | Normalize input and ask the repository to save |
| Repository | Read and write data | Save a record in the generated in-memory store |
| Module | Register providers and control visibility | Make the service available for injection |

Dependency injection (DI) means Xecute creates registered objects and passes their
dependencies through typed fields. `Arc<UserService>` is a shared reference to a
service, not a new service constructed for every call.

## Example: a valid POST

1. The server receives POST `/user` with a JSON body.
2. Server middleware applies configured HTTP policies.
3. The route extractor decodes `CreateUserDto` and checks its validation rules.
4. The controller calls the service (MVC) or command handler (CQRS).
5. The operation calls the repository, which creates a record.
6. The controller returns `201 Created` with that record; response middleware can wrap it.

```text
MVC:  HTTP → DTO → Controller → Service → Repository
CQRS: HTTP → DTO → Controller → Command/Query Handler → Repository
```

A GET list request has no JSON body to validate. Its query parameters are only
validated if you add a query DTO and use `#[query]`.

## Example: an invalid POST

Send `{"name":"A"}` to a generated create endpoint. JSON decoding succeeds,
but name validation fails. You receive `422` before the controller method or
repository runs. A malformed JSON document instead returns `400`; a missing JSON
content type returns `415`.

This validation belongs to HTTP extraction. Calling a service directly in Rust
does not automatically validate a DTO. Enforce business invariants in your
application/domain logic wherever they are required.

## Decide where a value comes from

| Request value | Handler input | Example |
| --- | --- | --- |
| JSON body | `#[body] payload: CreateUserDto` | POST body `{"name":"Munna"}` |
| URL segment | `#[param] id: u64` | `/user/42` with `#[get("/{id}")]` |
| Query string | `#[query] query: SearchQuery` | `/user?limit=10` |
| Headers | `headers: axum::http::HeaderMap` | Read `Authorization` or another header |
| URL-encoded form | `form: axum::extract::Form<ContactForm>` | HTML form submission |
| Raw text or bytes | `String` or `axum::body::Bytes` | A plain-text or binary body |

These are parameter fragments, not extra routes already generated by the CLI.
Put reusable DTO structs in `dto/mod.rs`; import them into the controller.
`#[body]` and `#[query]` DTOs need `Deserialize`, `Validate`, and `JsonSchema`.
A form DTO needs `Deserialize`; form validation must be called explicitly.

Use only one body-consuming extractor per handler, placed last. JSON, forms,
raw text, raw bytes, and multipart all consume the request body. Headers, path,
and query values can be used alongside that one body extractor.

## What a module import does

If `OrderService` needs `UserService`, the user module must export `UserService`
and the order module must import the user module. Both module definitions must
be registered in the application graph.

An import grants visibility; it does not automatically discover modules or mount
routes. The resource generator handles registration for generated features.
Manual assembly needs explicit definitions and routers.
